# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Single Vercel-deployed FastAPI app exposing webhook endpoints. Five webhook receivers, all Moco-sourced:

- `POST /api/moco-sync` — replicates Moco Activity create/update/delete into a *target* Moco account.
- `POST /api/bexio-expense-sync` — turns a Moco `Purchase:create|update` webhook into a Bexio supplier bill (with attachment).
- `POST /api/bexio-invoice-sync` — turns a Moco `Invoice:update` (status=sent) webhook into a Bexio customer invoice.
- `POST /api/brevo-contact-sync` — turns a Moco `Contact:create|update` webhook into a Brevo contact (lookup → create-or-update → SMS → add-to-list).
- `POST /api/supplier-invoice-ocr` — turns a Moco `Purchase:create` webhook (an email-imported draft) into a fully populated real Moco purchase by OCRing the attached PDF with Claude Vision and `POST /purchases`-ing a new entry tagged either `["OCR", "Auto"]` (fully resolved — released straight to `bexio-expense-sync`) or `["OCR", "Review pending"]` (held for a human), per `PurchaseReviewGate`. Already-paid card/POS receipts additionally get a Moco purchase payment registered so they don't show a phantom open balance.

The three external-sink endpoints replace n8n workflows that previously sat between Moco and the downstream systems (see `reference/` for the original exports). The OCR endpoint has no n8n predecessor — it's a new flow specified in `reference/SPEC_supplier_invoice_ocr.md`.

## Architecture

`api/index.py` is the Vercel Functions entrypoint and is intentionally thin: it owns request parsing, env-var loading, and the auth/filter pipeline, then dispatches to one of the service classes. The webhook pipeline runs in a fixed order — verify HMAC signature → check timestamp freshness → check account URL → check target → check event → parse JSON → (for moco-sync) filter by user → before any outbound work. The auth/parse plumbing is shared across the three external-sink endpoints (Bexio expense, Bexio invoice, Brevo contact) via `_handle_moco_dispatch_webhook`; the only per-endpoint inputs are the required env list, the expected `x-moco-target`, an `upstream_label` for error formatting, and a `build_service` factory.

Collaborators (one class per file):

- `api/moco_webhook_validator.py` — `MocoWebhookValidator`: HMAC-SHA256 signature check, ±300s timestamp window, account-URL match. Pure, no I/O.
- `api/moco_api.py` — `MocoAPI`: thin typed wrapper around the **target** Moco REST endpoints used by moco-sync (`list_projects`, `list_activities`, `create_activity`, `update_activity`, `delete_activity`).
- `api/moco_sync_service.py` — `MocoSyncService`: resolves source project/task names against the target account (falls back to configured defaults when no match), builds the activity payload, and dispatches to `sync_create` / `sync_update` / `sync_delete`.
- `api/moco_client.py` — `MocoClient`: reads from the attached Moco account (`/companies/{id}`, the paginated full supplier list via `list_suppliers` and the paginated full customer list via `list_customers` (`/companies?type=supplier`/`type=customer`, sharing a private `_list_companies` pagination helper — matching happens client-side in `MocoSupplierMatcher`), `/projects/{id}`), posts comments back (`/comments`), and downloads signed `file_url` attachments. Used by all three external-sink services (the Brevo flow uses only `post_comment`) and by the supplier-invoice OCR service (for both the PDF download and the supplier lookup); `list_customers` additionally feeds `EnergyCreditNoteService.is_evu_tagged_customer` (see below) — never used to set a purchase's `company_id`, so it doesn't compromise the supplier-only convention `list_suppliers` exists to enforce.
- `api/bexio_api.py` — `BexioAPI`: thin wrapper around the Bexio REST endpoints (`/2.0/contact[/search]`, `/2.0/accounts/search`, `/2.0/kb_invoice[/:id/issue|/comment]`, `/3.0/document_templates`, `/3.0/files` multipart upload, `/4.0/purchase/bills[/:id]`). Bearer auth — either a static `api_token` (used by tests) or a `token_provider` (production; a `BexioTokenProvider`). With a provider the OAuth access token is resolved **lazily on the first request and memoized** for the instance's life, so a refresh failure surfaces inside `service.sync()` where the endpoint's error mapping catches it (an eager resolution in `build_service` would escape that arm).
- `api/kv_client.py` — `KVClient`: a minimal Redis client speaking the RESP protocol over a `socket` (TLS via `ssl` for `rediss://`), parsed from the single `REDIS_URL` the Marketplace integration injects — stdlib only, no `redis-py` dependency. Wraps only `get`/`set`/`set_nx`/`delete` — the durable store for the rotating Bexio OAuth token. A fresh connection is opened per command (common path is one GET/webhook). Not a general Redis client. Transport failures raise `KVError` (a `URLError` subclass → 502 retry); a Redis `-ERR` reply raises `RedisCommandError`.
- `api/bexio_token_provider.py` — `BexioTokenProvider`: resolves a short-lived Bexio OAuth2 access token (Keycloak at `auth.bexio.com`). Bexio **rotates the refresh token on every refresh**, so token state lives in a durable KV blob (`bexio:oauth` = `{access_token, refresh_token, expires_at}`), not an env var. `get_access_token()` returns the cached access token while it's fresh (>60s of life); otherwise it refreshes under a KV lock (`bexio:refresh_lock`, `SET NX EX`) — serializing concurrent refreshes so Keycloak's reuse-detection can't kill the whole offline session — POSTs `grant_type=refresh_token`, and persists the **new** refresh token. The lock loser waits briefly for the winner to publish, then raises `BexioTokenRefreshContended` (a `URLError` subclass → 502 retry, no Telegram). Token-endpoint 4xx (revoked/expired refresh token) propagates as `HTTPError` → the endpoint's Telegram `bexio_error` alert (the signal to re-run `scripts/bexio_oauth_bootstrap.py`).
- `api/bexio_config.py` — hardcoded non-secret Bexio numeric IDs (user_id, owner_id, bank_account_id, mwst/currency/language defaults) and the project-label → revenue-account mapping for the invoice flow. The one exception is the per-Moco-user manual-bill bank routing (`manual_bank_account_id`), which reads from the `BEXIO_MANUAL_BANK_MAP` env var to keep staff first names out of the public source.
- `api/bexio_expense_sync_service.py` — `BexioExpenseSyncService`: contact find-or-create → account lookup → bill find-or-create-or-update (idempotent via `vendor`+`vendor_ref` search; skips non-DRAFT bills) → attachment upload → comment back to Moco. Branches on whether the Moco purchase carries an IBAN (QR/IBAN payment vs MANUAL). The payment **remark** (`payment.note`) is the same for both branches — `_payment_note` uses the Moco purchase `title` (on an OCR'd purchase that's `position_title`, i.e. the business purpose), falling back to composing supplier / Belegnummer / Zahlungszweck with empty parts dropped, then to `"-"`; capped at `PAYMENT_NOTE_MAX_CHARS` (80). Previously the IBAN branch read only Moco's `info` (the QR-bill Zahlungszweck), which is empty on most invoices, so QR payments carried a bare `"-"`. Every free-text field sent to Bexio (bill title, line-item title, `payment.note`) goes through `_bexio_text`, which maps the Unicode dashes Bexio rejects (em/en/figure/horizontal-bar/minus) to a plain ASCII hyphen, collapses the leftover whitespace, then truncates — normalize first so the cap counts what Bexio actually receives. The OCR prompt already asks for a plain hyphen as the `position_title` separator; this is the boundary guard, since the model writes German prose and can reach for an em dash anywhere in it. Moco keeps whatever the model wrote — this is a translation for one downstream system, not a correction. The receipt reference on `payment.booking_text` / `payment.message` (both carry `receipt_identifier`) is capped at `PAYMENT_RECEIPT_REF_MAX_CHARS` (35) — Bexio's own limit, learned from a live 400 (`payment.booking_text size must be between 1 and 35`) on a Hornbach Kassenbon whose OCR'd invoice number was the 40-char till-slip transaction line. The cap is deliberately NOT applied to `vendor_ref` (the idempotency key `_find_existing_bill` searches on — Bexio accepted the full length in the same request, and truncating it would make replays miss the bill) nor to `reference_no` (a truncated payment reference is a wrong payment).
- `api/bexio_invoice_sync_service.py` — `BexioInvoiceSyncService`: gates on `status=sent`, fetches the Moco project, resolves the revenue account from project labels, creates the invoice, cross-comments both sides, and transitions Bexio state DRAFT → Open via `/issue`.
- `api/brevo_api.py` — `BrevoAPI`: thin wrapper around the Brevo (ex-Sendinblue) REST endpoints (`/v3/contacts[/:identifier]`, `/v3/contacts/lists/:id/contacts/add`). Auth via `api-key` request header (not `Authorization: Bearer`). `get_contact` maps a 404 to `None` so the caller can branch on existence without exception handling.
- `api/brevo_contact_sync_service.py` — `BrevoContactSyncService`: skip-if-no-work-email → `GET /v3/contacts/{email}` lookup → create-vs-update branch → update SMS attribute with the n8n-style normalized phone → add to configured Brevo list. Comment back to Moco only on create. SMS-update and list-add failures are logged but do not fail the sync.
- `api/anthropic_ocr_client.py` — `AnthropicOcrClient`: thin wrapper around Anthropic's `POST /v1/messages` (Claude Sonnet 4.6, vision-capable). Sends a PDF as a base64 `document` content block, parses the structured JSON response into an `InvoiceData` dataclass. `extract(pdf, subject=…)` takes the operator-typed subject of a hand-uploaded draft as per-request context — it rides in the **user turn** (so `SYSTEM_PROMPT` stays a static, per-request-identical string), fenced in guillemets and labelled as data rather than instruction. It feeds exactly one field: `position_title`, the merged booking title (subject + document reading, capped at the 80 chars Bexio truncates to), kept **separate from** `description` so that stays a pure reading of the document for the Gutschrift / energy-credit-note paths that also read it. The prompt tells the model to drop a subject that's merely a file name — about half the live manual subjects are (`trennscheibenblätter.pdf`) — and to echo `description` verbatim when no subject was supplied. The parser is robust to preamble (Sonnet sometimes thinks out loud before emitting JSON when the prompt enforces length checks); QR-references are stripped to digits-only and nulled unless they are exactly 27 digits AND their **modulo-10-recursive check digit** matches (the 27th digit is a checksum over the first 26 — length alone let a length-preserving misread through, and a wrong reference posts the payment against the wrong invoice at the supplier); IBANs are stripped of non-alphanum, uppercased and mod-97 validated. Errors: 4xx/5xx → `AnthropicOcrError` with `status_code` set; bad-JSON model output → `AnthropicOcrError(status_code=None)`. URL errors propagate.
- `api/moco_purchase_client.py` — `MocoPurchaseClient`: purchase-specific writes on the Moco account. Six endpoints: `GET /purchases/drafts/{id}` (note the `drafts/` prefix — draft purchases live in a different URL space and `GET /purchases/{id}` 403s on a real draft), `GET /vat_code_purchases` (vat-code lookup table used by the OCR service to map OCR'd `vat_rate` to `vat_code_id`), `POST /purchases` (the create-real-purchase endpoint; attachments ride along as `file: {filename, base64}` JSON, **not** multipart), `GET /purchases/{id}` (read a real purchase — a DIFFERENT URL space from the draft one above, each 403s on the other's ids; used to re-fetch an auto-released purchase before the Bexio hand-off), `POST /purchases/payments` (settle an already-paid receipt — note the **top-level** collection: the purchase is named by the `purchase_id` body field, not the URL; no idempotency key, and once a payment exists `DELETE /purchases/{id}` is refused), and `POST /comments` (commentable_type="Purchase"). The generic company listing (`list_suppliers`) lives on `MocoClient` instead — it's not purchase-specific and sits next to `get_company(id)` there.
- `api/moco_supplier_matcher.py` — `MocoSupplierMatcher`: matches the OCR'd supplier name against the full Moco supplier list in three tiers of increasing tolerance — (1) **exact**: case-insensitive whitespace-collapsed equality; (2) **substring**: containment either direction on alnum-collapsed umlaut-folded forms (min 3 chars per side), catching "Brack.ch" → "BRACK.CH AG" and "Debrunner Acifer AG, 3014 Bern" → "Debrunner Acifer AG"; (3) **normalized**: token-set *equality* (not subset) after folding umlauts/accents and dropping legal-form filler (AG, GmbH, Sàrl, & Co, …), catching reordering like "Mueller + Partner AG" → "Partner Müller". Each tier links only on a unique hit; multiple hits at a tier → `ambiguous` and the matcher STOPS (no fallthrough to a looser tier — same conservative semantics as `MocoProjectResolver`/`SmartmeProjectMatcher`; a company-less purchase beats a mis-linked one). `SupplierMatch.candidates` carries ties for diagnostic output in the batch/single-draft scripts.
- `api/vat_code_resolver.py` — `VatCodeResolver` (+ the `VatDecision` it returns): picks the line item's `vat_code_id` from the `GET /vat_code_purchases` catalog. Four tiers — OCR'd `vat_rate` → matched supplier company's default rate (`supplier_vat.tax`, translated through the same catalog) → the code flagged as the account-wide default → a **payment-method floor**: `already_paid_by_card` books the active 0% domestic code, everything else the 8.1% standard rate. Only an account with no active code at the wanted rate leaves the field off (Moco 422 → the service's silent-skip + Telegram path). The floor exists because neither live Moco account flags an account default, so tier 3 never fires and card receipts that print no VAT line (Swiss slips under CHF 400 needn't) used to 422 unconditionally. **Special-scheme codes are only picked as a last resort**: both accounts carry two active `tax: 0.0` codes and list the `reverse_charge` "(Ausland)" one *first*, so plain codes win every rate match and a `reverse_charge`/`intra_eu` code is returned only when it's the sole match. `VatDecision.source` (`ocr` / `supplier` / `account_default` / `fallback_zero` / `fallback_standard`) is what `PurchaseReviewGate` branches on — `.guessed` is true for the two floor tiers. Pure, no I/O: the service fetches the catalog and hands it in, so both operator scripts run the real chain instead of a mirror of it. See `specs/SPEC_vat_code_fallback.md`.
- `api/moco_category_resolver.py` — `MocoCategoryResolver`: picks the line item's `category_id` (Buchhaltungs-Konto) from the `/purchases/categories` catalog, indexed by `credit_account`. Chain: matched project's `Aufwandkonto` custom field → matched supplier company's `Aufwandkonto` custom field → already-paid-by-card omit (a card receipt without an explicit override gets NO default; reviewer picks by hand) → hardcoded `4000` default (Wareneinkauf). An override that's set but unmapped is a final omit, NOT a fallthrough — an explicit account that misses must not silently reroute to a different one.
- `api/purchase_review_gate.py` — `PurchaseReviewGate`: decides whether a newly OCR'd purchase carries `Review pending` (held for a human) or `Auto` (released straight to the Bexio expense sync). Pure, no I/O. Auto-releases only when **all** of: a supplier company matched, the category is *trusted*, `confidence >= AUTO_RELEASE_CONFIDENCE` (0.90 — deliberately a separate constant from `supplier_invoice_ocr_service.CONFIDENCE_THRESHOLD` (0.85), which only picks a Telegram emoji; tuning alert noise must not retune a gate that lets purchases reach Bexio unreviewed), it isn't a credit note, and the VAT rate wasn't guessed (`VatDecision.guessed` — the `VatCodeResolver` payment-method floor; in practice this only bites bank-transfer bills, since card receipts are already held by the category chain). A category is trusted by its `CategoryDecision.source`, not merely by being set: `supplier` always; `project` only on an `exact`/`substring` `ProjectMatch.tier` (never `token-overlap`, where any single shared token counts — the `Aufwandkonto` is equally deliberate either way, it's the *match* selecting the project that's weaker); `default` (the 4000 fallback) yes — which is unreachable for already-paid card receipts because `MocoCategoryResolver` short-circuits at `already_paid` first, so card-receipt strictness falls out of the existing chain and this gate needs no payment-method branch. `ReviewDecision` carries `review_pending`, the finished `tags` list (tag policy lives here, not in `_build_create_payload`) and operator-facing German `reasons` naming which conditions held it. Both operator scripts call the same class for their `REVIEW` preview column, so the preview can't drift from the real rule. Consequence recorded deliberately: for a **bank-transfer** bill the 4000 fallback nearly always resolves, so the category condition rarely bites there and the effective gate is company + confidence. See `specs/SPEC_purchase_payment_already_paid.md`.
- `api/supplier_invoice_ocr_service.py` — `SupplierInvoiceOcrService`: download PDF from the draft's `file_url` → OCR → look up supplier company via `MocoSupplierMatcher` (link `company_id` only on a unique tiered match; the full record is then fetched once via `get_company` — the list shape carries neither `default_vat_code_purchase_id` nor `custom_properties` — and shared by the vat and category chains) → recover a missing `iban` from the matched supplier's Moco record (`_apply_supplier_iban_fallback` — fills a GAP only, never overrides an IBAN the model read, and re-validates mod-97 since a hand-entered IBAN isn't automatically well-formed; runs before payload construction because `_payment_method_for` / `_resolve_reference_and_info` branch on it, and the OCR comment marks the value "aus Lieferant-Stammdaten" so the reviewer knows which claim they're confirming) → resolve `vat_code_id` via `VatCodeResolver` (OCR `vat_rate` → supplier company default → account-wide default flag → the payment-method floor of 0% / 8.1%) → resolve `category_id` via `MocoCategoryResolver` → `POST /purchases` with a title chain of `position_title` → `description` → `supplier_name` → `"OCR-importierte Rechnung"` (used for BOTH the purchase title and the single line item's, as before) + base64-PDF + tags decided by `PurchaseReviewGate` (`["OCR", "Auto"]` when auto-released, `["OCR", "Review pending"]` when held, plus `"Gutschrift"` on a credit note) + payment_method derived from OCR (`bank_transfer_swiss_qr_esr` when a QR-reference is present, else `bank_transfer`) → two comments on the new purchase: **provenance** (📧 Email-Quelle — Betreff + Von + body — when `email_from` is set, else 📎 Manueller Upload — Betreff + Hochgeladen von; mutually exclusive, and the only surviving record of where the purchase came from once the draft is deleted) and the OCR summary — led by the **verdict** (✅ auto-released, or ⚠️ held with `ReviewDecision.reasons` spelled out and the "Review pending"-Tag removal as the next action), then the four resolved-against-Moco fields (Lieferant / Konto / MWST / Kommission) carrying ✓/✗ markers that mirror the batch script's table — MWST is ✗ exactly when the rate came from the resolver's floor, i.e. when it's an assumption the reviewer has to confirm, then the plain OCR readings unmarked. Operator-facing strings are German throughout: `CategoryDecision.source` is mapped via `CATEGORY_SOURCE_LABELS` and its internal English `reason` is replaced by `_category_comment_text` (same split for `VatDecision.source` via `VAT_SOURCE_LABELS` / `_vat_comment_text`), so log vocabulary never leaks into a comment → Telegram (confidence-routed; Gutschrift always triggers a Vorzeichen-prüf alert that overrides the confidence path). A **QR-reference with no IBAN** — or its mirror, a **QR-IBAN with no QR-reference**, which is the more dangerous one since a QR-IBAN is only payable *with* a reference and nothing can recover a per-invoice reference — appends a warning line to that same message (mutually exclusive; one Telegram per draft stays the rule): the Zahlteil was legible enough for a 27-digit reference but not the IBAN beside it, and no supplier record could recover one — downstream that silently becomes a MANUAL Bexio payment with no Zahlungsausgang. When an `EnergyCreditNoteService` was configured and its three detection signals all declined a genuine credit note (i.e. it fell through to this generic path rather than being routed there), the Gutschrift alert gets an extra soft-conditional line ("Falls dies eine EVU-Produktions-Gutschrift ist: EVU-Tag … prüfen, oder ein Stromproduktion-Projekt dafür anlegen") — phrased as "if" since a routine, unrelated credit note (e.g. a hardware return) would trigger the same fall-through; omitted when `energy_credit_note=None` since detection was never attempted. Credit-note detection negates the line item total before posting (operator can flip back during review). Receipts the document says were **already settled** at the point of sale (`already_paid_by_card` → `payment_method=credit_card`) additionally get a Moco purchase payment registered right after the create (`POST /purchases/payments`, `total` from the create response's server-computed `gross_total` — not the OCR figure, or a rounding cent leaves a residual — `date` from the purchase date, not today), so they don't sit showing an open balance on money that already left the account. A 💳 comment is posted on the purchase right after, explaining that the settle was automatic (best-effort, and after the payment — a failed comment must not make the caller think the settle didn't happen). Best-effort like the project assign: a failure warns on the same Telegram message and the sync still reports ok. Skipped for credit notes (card-refund sign convention unverified) and non-positive amounts. Deliberately **independent of the review decision** — a held receipt is settled too, at the cost of the purchase becoming undeletable and the payment going stale if the reviewer corrects the total. **Auto-released purchases are handed straight to `BexioExpenseSyncService`** rather than waiting for a `Purchase:create` webhook to come back round: Moco does not deliver that webhook for purchases created through the API (confirmed across 11 live auto-released purchases — ten never synced, and the one that did got its bill only after a human edited its labels in the UI, i.e. from an *update*). The purchase is re-fetched via `get_purchase` so the sync sees the shape a webhook would have delivered (`file_url`, expanded `items[].category`) rather than the create response. Held purchases are never pushed — the tag exists so a person looks first, and the expense sync's own first gate would refuse them anyway. Best-effort like the project assign: a Bexio 4xx must not escape to `index.py` (it would flip the run to ok=false) and a 5xx must not either (a webhook retry would re-run the paid OCR); failures warn on the same Telegram message and the sync still reports ok. The collaborator is optional (`bexio_expense=None`), so an instance without `BEXIO_CLIENT_ID`/`BEXIO_CLIENT_SECRET`/`REDIS_URL` keeps the old wait-for-webhook behaviour instead of failing the endpoint. The original draft is auto-deleted after a successful create (best-effort: 404 = already gone, other failures → Telegram alert, sync still ok=true). Attachment-less drafts whose subject (`title`) contains "Sicherheitshinweis" or "Zustellungshinweis" (case-insensitive) are notification emails misrouted into the invoice inbox: the draft is deleted silently (info log, no Telegram; a failed delete logs a warning only). Optional Telegram (`None` skips the alerts so service tests can stay terse).
- `api/smartme_project_matcher.py` — `SmartmeProjectMatcher`: maps a smart-me "Objekt" string (e.g. `"Gesamtverbrauch (Hauptstrasse 33 Leimbach)"`) to exactly one Moco project labeled `ZEV` or `Eigenverbrauch`. Tier 1: **Kommission custom-field equality** — the operator pins a mapping by putting the smart-me object name into the project's `Kommission` field; a project matches when its normalized Kommission *equals* one of the Objekt's segments (full string / pre-parenthesis part / parenthesized group content). Equality, not substring — the parenthesized part names the ZEV community, and the community project's own Kommission is a substring of it (containment would route every consumer bill to the community project). Tier 2 (unpinned projects): **best-token-overlap score** over project names (tokenized on non-alphanumerics, `MIN_TOKEN_LEN=1` so house numbers survive — they disambiguate projects that share a village token like "Oberkirch"; unique max wins, top-tie → ambiguous; generic tokens like "EFH" can still tie two projects — that's what tier 1 is for, and the Telegram alert says which Kommission field to fill). Deliberately NOT `MocoProjectResolver.resolve()`, whose any-shared-token tier would report every same-village project as ambiguous. Also exposes `project_energy_label` (ZEV wins over Eigenverbrauch when both tags are present).
- `api/smartme_energy_expense_service.py` — `SmartmeEnergyExpenseService`: handles smart-me "Energiekostenabrechnung" drafts — PVcontracting's **own outgoing** energy statements that land in the same invoice inbox but must never become supplier purchases. Detection (`is_smartme_draft`, 2-of-3 rule: title contains "energiekostenabrechnung" / sender-or-body contains "no-reply@smart-me.com" / body contains "objektname" or "abrechnungszeitraum") runs inside `SupplierInvoiceOcrService.process` **before** the file_url gate; detected drafts are delegated here. Flow: download PDF → `extract_energy_bill` (own OCR schema: Objekt, Netto-Betrag, Abrechnungszeitraum, Rechnungsdatum, Rechnungsnummer) → `SmartmeProjectMatcher` → `POST /projects/{id}/expenses` with the operator's manual conventions (quantity 1, unit "Netto", unit_price = Netto-Betrag, unit_cost 0, billable, budget_relevant, service_period = Abrechnungszeitraum, PDF attached; title "Solar- und Netzstrom gemäss Beilage" for ZEV / "Solarstrom Eigenverbrauch gemäss Beilage" for Eigenverbrauch) → best-effort draft delete + Telegram summary (the review hook — expenses carry no "Review pending" tag). No-match / ambiguous / no-attachment / no-Netto-Betrag → Telegram alert + best-effort comment on the draft (`commentable_type="PurchaseDraft"`), draft **stays** in the inbox, ok=true skip. OCR/Moco errors propagate into the endpoint's existing 4xx/5xx mapping.
- `api/stromproduktion_project_matcher.py` — `StromproduktionProjectMatcher`: maps an EVU (local energy supplier) production credit note's OCR'd `Objekt` + supplier name to exactly one Moco project tagged `Stromproduktion`. Tier 0: **Kommission custom-field equality** (operator pin), checked across all `Stromproduktion` projects regardless of supplier — an explicit pin always wins. Tier 1: **required customer-name filter** — only projects whose `customer.name` plausibly matches the OCR'd supplier name participate further; Moco holds two separate company records per real-world EVU (one `type: "customer"` used as `project.customer`, one `type: "supplier"` used by `MocoSupplierMatcher`, sharing a name but not an id — e.g. "CKW AG" vs "CKW AG (Lieferant)", both tagged `Lokaler Energieversorger (EVU)`, confirmed live), so matching goes through name, never id equality. Zero tier-1 candidates → `no_match`, never a fallthrough to another EVU's projects. Tier 2: **best-token-overlap** between the Objekt and each surviving candidate's project `name`, tokenized with an extra letter/digit-boundary split (`_addr_tokens`) beyond the usual non-alphanumeric split — Moco's Contracting-project names fuse the house number (`"Meierhofweg10_Emmen"`) while OCR'd Objekt text spaces it (`"Meierhofweg 10"`); plain tokenizing finds zero overlap on the exact live example this feature was built against (draft `3143995`).
- `api/moco_invoice_client.py` — `MocoInvoiceClient`: thin wrapper around Moco's sales-invoice endpoints (`GET /vat_code_sales`, `POST /invoices`, `POST /invoices/{id}/attachments`) — the invoice-domain counterpart to `MocoPurchaseClient`. No `update_status` method: created invoices are deliberately left at `status: "created"`, never transitioned to `"sent"` (see `EnergyCreditNoteService`).
- `api/energy_credit_note_service.py` — `EnergyCreditNoteService`: handles EVU (local energy supplier, e.g. CKW) production credit notes — quarterly statements that combine a small consumption invoice with a much larger production credit ("Gutschrift"/"Rücklieferung") for electricity PVcontracting fed back into the grid; this is PVcontracting's own outgoing revenue and must never become a supplier purchase. Detection needs THREE independent signals, any one sufficient (`invoice.is_credit_note` AND (the matched SUPPLIER-type company tagged `Lokaler Energieversorger (EVU)` OR `EnergyCreditNoteService.is_evu_tagged_customer` finds a CUSTOMER-type company match carrying that tag instead OR `EnergyCreditNoteService.has_matching_project` finds an actual `Stromproduktion` project for the OCR'd supplier name)) — confirmed live that the supplier-type tag alone is unreliable in two different ways: Moco can hold it on one of an entity's two company records but not the other (EGBB's `type: "customer"` record was tagged, its `type: "supplier"` "(Lieferant)" record — the one `MocoSupplierMatcher` actually links — had `tags: []`), or the entity can have NO `type: "supplier"` record at all (BKW — only a `type: "customer"` record exists, tagged, since the relationship an energy credit note represents is PVcontracting selling production back to the EVU, i.e. the EVU as a customer). `is_evu_tagged_customer` reuses `MocoSupplierMatcher`'s own tiers against a `customer_matcher` built from `MocoClient.list_customers()`; the project-existence check (`has_matching_project`) remains a further, independent fallback that can only fire when there's a real project to route to. Runs inside `SupplierInvoiceOcrService.process` **after** the general OCR + supplier lookup (unlike smart-me, there's no cheap pre-download signal for this document class); detected drafts are delegated here. Flow: a second, targeted OCR pass (`extract_energy_credit_note`) pulls the Objekt of the production-credit section SPECIFICALLY (`objekt`, the PRIMARY project-matching signal) plus the Objekt of the document's top-level summary (`objekt_top_level`, a FALLBACK signal — see below), the document's TOP-LEVEL gross Gutschriftsbetrag (`gross_amount`, inkl. MWST), and `vat_rate` — the top-level gross figure, not either subsection's own Nettobetrag, since it already nets the consumption section against the production section and is the actual amount that moves (booking a subsection's Nettobetrag alone would misstate the credit; see `specs/SPEC_energy_credit_note.md`, decision D6). The bookable ex-VAT amount is then DERIVED, not OCR'd: `net_amount = gross_amount / (1 + vat_rate)` (`_derive_net_amount`) — a missing `gross_amount` or `vat_rate` blocks the derivation entirely rather than guessing a rate. `gross_amount` is always normalized to a positive magnitude in code (`abs()`, not just prompt wording) since some EVUs (EGBB) frame their entire statement as a negative payout figure while others (CKW) print it plain-positive → `StromproduktionProjectMatcher` resolves the project via `_match_project`, which tries `objekt` first and falls back once to `objekt_top_level` only when the primary attempt is `no_match`/`empty` (never on `ambiguous`) — confirmed live (draft 3143993, a CKW vZEV community statement) that a production section's own Objekt can be a generic label with no site identifier ("vZEV Überschuss") while the top-level summary's Objekt does carry one (decision D7) → `POST /projects/{id}/expenses` (title `"Stromproduktion <Leistungszeitraum>"` e.g. "2026/Q2", quantity 1, unit "x", unit_price = derived net amount, unit_cost 0, billable, NOT budget_relevant, service_period = Abrechnungszeitraum, PDF attached) → `POST /invoices` linking that expense via `items[].expense_ids` (Moco marks the expense billed automatically), `status="created"` — **deliberately never transitioned to "sent"**; sending is a manual step the operator performs later in the Moco UI, and the existing `bexio-invoice-sync` cascade fires then, automatically, no new code needed → `POST /invoices/{id}/attachments` with the same PDF → best-effort draft delete + Telegram summary with a link to the new invoice, noting it still needs manual review + sending. VAT-code resolution: OCR'd `vat_rate` matched against `GET /vat_code_sales` → the active code at the account-standard 8.1% → the first active code (last resort). Anything that prevents a confident booking — no project match, ambiguous match, missing `gross_amount`/`vat_rate` (blocks the net-amount derivation), missing/unparseable Abrechnungszeitraum — keeps the draft (Telegram alert + comment, `commentable_type="PurchaseDraft"`, draft NOT deleted), mirroring `SmartmeEnergyExpenseService`'s keep-draft posture exactly. Expense/invoice/attachment `HTTPError`s are not internally swallowed (same as smart-me's `create_project_expense`) — they propagate to `index.py`'s existing 4xx/5xx mapping; `supplier_invoice_ocr_service.py` tags this branch's errors (`in_energy_credit_note_branch`) so they bypass the generic purchase-flow's own duplicate-receipt 4xx swallow.
- `api/telegram_notifier.py` — `TelegramNotifier`: thin `POST https://api.telegram.org/bot<token>/sendMessage` wrapper (bot token in the URL path, `chat_id`+`text` in the JSON body). `notify(text)` is best-effort — swallows every transport error and returns a bool, never raising into an already-failing request path (per `feedback_soft_failure_logging`). Instantiated per-request in `index.py` and injected into `BexioExpenseSyncService`.

**moco-sync — stateless source↔target link**: the target activity's `remote_id` is set to `f"{MOCO_SUBDOMAIN}:{source.id}"` (e.g. `"solar:1064823757"`). Update and delete lookups scan `/activities?from=DATE&to=DATE` and filter by exact `remote_id` match. Moco's `remote_service` field is server-side enum-validated (github / trello / jira / asana / …) — sending an arbitrary string returns `422 {"remote_service":["ist kein gültiger Wert"]}`. So we leave `remote_service` blank and pack the namespace into `remote_id` instead. If no matching target activity is found on update, `sync_update` falls through to POST (upsert) — a missed create-webhook self-heals on the next update. On delete, `sync_delete` raises `TargetNotFoundError`, which the handler treats as an application error (Telegram alert + **HTTP 200 `ok=false`**, so Moco stops retrying — see the 2xx/5xx contract below). The dateless lookup window for delete is intentionally tight (currently 14 days) to stay within a single Moco `/activities` page — we don't follow pagination.

**bexio-expense-sync — idempotency**: identifies an existing bill by `GET /4.0/purchase/bills?vendor={company.name}&vendor_ref={receipt_identifier}`. If the first result is DRAFT, fetch the full bill via `GET /4.0/purchase/bills/{id}` to preserve `document_no` and `split_into_line_items`, then PUT the new payload. If status is anything other than DRAFT, skip with `{"skipped": "bill_not_draft"}` (n8n's "bill closed" branch). If no bill matches, POST. The IBAN branch sets `payment.type = QR` (when a reference is also present) or `IBAN` and routes to `bexio_config.BANK_ACCOUNT_ID`; the MANUAL branch routes via `manual_bank_account_id(user.firstname)` from `BEXIO_MANUAL_BANK_MAP`. Attachments: download the Moco `file_url` (a pre-signed URL — no auth header), upload to `POST /3.0/files`, attach the returned UUID to the bill. Skipped when the existing bill already carries an attachment_id — in that case the existing `attachment_ids` are copied into the PUT payload so Bexio (which replaces rather than merges this field) doesn't detach the file. Bookkeeping account is looked up by `account_no` from `items[0].category.credit_account` (falls back to `supplier_credit_number`, then to `bexio_config.DEFAULT_BOOKING_ACCOUNT_NO`).

**bexio-expense-sync — book + outgoing payment**: after both create and update, the service moves the bill DRAFT → BOOKED via `PUT /4.0/purchase/bills/{id}/bookings/BOOKED`, then POSTs an outgoing payment to `/4.0/payment/outgoing-payments` (QR or IBAN switched by `reference`, with `fee_type=NO_FEE` only for plain IBAN-without-reference). Mirrors the n8n "Set Bill to Booked → Create Outgoing Payment → Comment Booked" chain but extends it to the update path too — on update the upstream `bill_not_draft` skip guarantees we're working on a DRAFT bill, so book+pay can run safely. **MANUAL bills (no IBAN) skip the step silently** — Bexio rejects MANUAL outgoing-payment payloads when `message` / `booking_text` / `reference_no` are set (`400 message is not allowed for [MANUAL] payment type`), and routine cash bills don't benefit from auto-booking; alerting on every one would spam Telegram. On success a second Moco comment is posted ("Lieferantenrechnung … auf gebucht gesetzt und Zahlungsausgang erstellt"). On any failure (e.g. payment already exists for the bill on a replay) the step is soft-failed: log + Telegram alert with the Bexio bill URL and the Moco purchase URL, sync still returns ok=true since the bill itself is the authoritative side effect. The Moco IBAN is normalized (non-alphanumerics stripped, uppercased) before it hits either Bexio endpoint — Bexio's outgoing-payment validator rejects whitespace as "illegal characters" even though bill-create is more lenient. The sender (own-company) fields embedded in every outgoing payment come from `BEXIO_OUTGOING_PAYMENT_SENDER` (JSON env var with keys `name`, `iban`, `bank_name`, `bc_no`, `street`, `house_no`, `postcode`, `city`, `country_code`, `bank_account_id`) — not committed since the IBAN shouldn't be in a public repo. Missing/malformed env → same Telegram alert, book+pay skipped.

**bexio-invoice-sync — idempotency + state transition**: Bexio's `api_reference` field carries the Moco invoice identifier; the create payload sets it so duplicates can be reasoned about in Bexio's UI. After `POST /2.0/kb_invoice`, the service calls `/issue` to move the invoice DRAFT → Open (pending payment). `/issue` failures are logged but do not fail the sync, since the invoice is already created in Bexio and Moco would otherwise retry and duplicate. (`/set_pending` is intentionally NOT called — Bexio 404s it once the invoice is already issued.)

**brevo-contact-sync — idempotency**: Brevo identifies contacts by email, so `GET /v3/contacts/{work_email}` is the idempotency key. 404 means the contact doesn't exist yet and we POST; any other response means we PUT. `create_contact` sends `updateEnabled: false` so a concurrent producer can't silently overwrite via the create path. Phone normalization mirrors the n8n JS exactly (`+`/`00` prefixes preserved, single leading `0` dropped, whitespace stripped) so the SMS attribute stays consistent with whatever the previous workflow wrote. `BREVO_LIST_ID` is per-environment and lives in env (not config) so dev/staging/prod can target different lists.

**Comments back to Moco**: all three external-sink services POST to `/api/v1/comments` on the Moco account so the downstream URL is discoverable from inside Moco. Brevo only posts on the *create* path (matches the n8n flow). Comment failures are logged and swallowed — the upstream mutation is the authoritative outcome.

**Telegram notifications + the 2xx/5xx contract**: ports the n8n `Error Trigger → Send Error to Telegram` handler, but with a deliberate HTTP-status split (`index.py`'s `_app_error`). The dividing line is *can a webhook retry fix this?*

Every outbound Telegram message **leads with a status icon** so the chat is scannable: ❌ nothing was created (hard failure), ⚠️ needs a human (skip, soft-failed side step, low-confidence result), ✅ done cleanly. The four n8n-ported Bexio messages (`_notify_skip_with_entity`, `_notify_bill_closed`, `_notify_book_pay_failure`, `_notify_no_customer`) predated the convention and were brought in line; the existing skip tests assert the prefix so it can't regress.

- **Application errors** — failures a retry can't fix: an upstream `HTTPError` with a **4xx** status (the external system rejected our request), an unexpected internal `Exception`, and the moco-sync delete `TargetNotFoundError`. These fire a Telegram alert (endpoint path, event, source id, error detail) and **ACK with HTTP 200 `{"ok": false, "event", "error"}`** so Moco stops retrying. Telegram now carries the visibility the old non-2xx + delivery-log used to.
- **Infrastructure failures** — transient, retry-worthy: `URLError` (upstream unreachable) and an upstream `HTTPError` with a **5xx** status. These surface as **HTTP 502** so Moco retries, and are **NOT** notified — a flapping upstream would otherwise spam the chat once per retry.
- **4xx auth/validation rejections** (bad signature, stale timestamp, wrong target) are unchanged: rejected pre-work with their own 401/422, never notified.
- **moco-sync user-filter** is a routine *skip*, not a rejection: an activity from a user other than `MOCO_USER_ID_FILTER` **ACKs with HTTP 200 `{"ok": true, "event", "skipped": "user_filter"}`** and logs at `info`, never notified. A 422 here would make Moco retry every non-filtered user's activity forever (a retry can't change the activity's user), so it must be 2xx — same reasoning as the invoice `status_not_sent` / brevo `no_work_email` silent gates.

Additionally, the two Bexio services DM the chat on genuine business-rule **skips** (not on the normal gates): `BexioExpenseSyncService` on no-company / no-account / bill-not-DRAFT (with the Moco purchase deep-link), and `BexioInvoiceSyncService` on no-customer (with the Moco invoice deep-link). These mirror the n8n `…Notification to Telegram` nodes. The invoice `status_not_sent` and brevo `no_work_email` gates stay **silent** — they're routine (fire on every draft edit / on every contact without a work email) and would spam, so `BrevoContactSyncService` takes no notifier at all. The two Bexio services take an optional `telegram` collaborator (defaults to `None`) so service unit tests can omit it; all sends route through `TelegramNotifier.notify`, which never raises.

Required env vars are listed in `REQUIRED_ENV_MOCO_SYNC` / `REQUIRED_ENV_BEXIO_SYNC` / `REQUIRED_ENV_BREVO_SYNC` / `REQUIRED_ENV_SUPPLIER_INVOICE_OCR` in `api/index.py` — the handler fails fast with a 500 if any are missing. `TELEGRAM_BOT_TOKEN` + `TELEGRAM_CHAT_ID` (shared constant `REQUIRED_ENV_TELEGRAM`) are required by all four. The two Bexio endpoints require `BEXIO_CLIENT_ID` + `BEXIO_CLIENT_SECRET` (OAuth app) and `REDIS_URL` (the single native connection string injected by the Marketplace Redis integration) instead of a static API token. The OCR endpoint additionally needs `ANTHROPIC_API_KEY` (Claude Vision) and *optionally* the three Bexio keys (`OPTIONAL_ENV_BEXIO_HANDOFF`) that enable the auto-release hand-off — deliberately optional rather than required, so a missing Bexio credential degrades the hand-off instead of 500ing the whole OCR endpoint; the VAT code on POST /purchases is resolved dynamically per invoice by `VatCodeResolver` (OCR vat_rate → supplier company default → account-wide default flag → a 0%/8.1% payment-method floor), so there's no env-var default. All collaborators are instantiated per-request inside `index.py`; they don't share state across invocations.

**bexio auth — OAuth2 token lifecycle**: the Bexio integration authenticates with OAuth2 (Keycloak at `auth.bexio.com`), not a personal access token (PATs expire after 60 days). Bexio rotates the refresh token on every refresh, so the token state can't live in an env var — it's kept in a durable KV blob (`bexio:oauth`) in Redis and managed by `BexioTokenProvider` (cache the ~1h access token → refresh under a lock → persist the rotated refresh token). The initial refresh token is minted once, locally, by `scripts/bexio_oauth_bootstrap.py` (a one-time Authorization Code Flow with `offline_access` that seeds `bexio:oauth`); re-run it only if the offline session dies (≈1 year idle, or a revoked token — you'll get a Telegram `bexio_error` alert). Provision Redis via the Vercel Marketplace; the integration injects a single `REDIS_URL` connection string (`rediss://…`), which `KVClient` speaks natively (RESP over a socket — no `redis-py` dep).

Vercel routing: `vercel.json` is empty (`{}`); Vercel's Python builder auto-detects the FastAPI `app` in `api/index.py` and routes all paths through it. Do not add a `vercel.json` `routes`/`rewrites` block unless you also restructure the entrypoint.

## Conventions

- One class per file; the entrypoint just wires imports together (see auto-memory `feedback_one_class_per_file`).
- Stick to `urllib` for outbound HTTP unless there's a reason to add a dependency — the service currently has zero runtime deps beyond FastAPI.
- The `reference/` directory contains n8n workflow JSON exports used as behavior references for the Moco integrations being ported here. It is gitignored and should not be edited or committed.
